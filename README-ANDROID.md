# Mobcode — Android (Capacitor) README

**Mobcode — Your code. Your agent. Anywhere.**
Native Android build of the existing Mobcode PWA, packaged with Capacitor 8.

> **Personal/private build notice:** the packaged backend (the Mobcode companion server,
> described below) fronts a single OpenCode workspace. This APK is intended for its
> owner's own phone. It is **not** a multi-user public deployment until the backend
> adds per-user workspace isolation.

---

## 1. What was inspected (Phase 1 findings)

| Area | Finding |
|---|---|
| App type | Vanilla-JS **PWA** (no framework, no React Native anywhere). ES modules, no bundler. |
| Frontend entry | `public/index.html` → `<script type="module" src="/app/js/main.js">` |
| Build scripts | Only `npm run build:icons` (`scripts/make-icons.mjs`). No web bundler — plain ES modules served statically. |
| Routing / navigation | Custom stack router (`window.__nav` in `main.js`) + bottom tab bar (`index.html`), programmatic views in `views.js`. |
| API integration | `public/app/js/api.js` (`MobcodeApi`) — same-origin companion proxy (`/__mobcode/*` injected on server) or a direct OpenCode URL; SSE via `/api/event` EventSource. |
| Authentication | OpenCode HTTP basic auth (`opencode:<password>`) is injected by the companion proxy; clients never hold credentials in this mode. Direct mode supports a password header. |
| PWA | `public/manifest.webmanifest`, `public/sw.js` (app-shell cache only — API/SSE traffic is never cached). |
| Dependencies | Zero runtime npm packages originally; dev tooling only (`scripts/`). |

**Chosen approach: Capacitor 8** (web/PWA → native WebView shell). No second,
competing mobile implementation was created; the Android app **is** the existing
Mobcode UI with a native layer added on top.

## 2. Architecture

```
MOBCODE ANDROID APP (this APK)
        │  HTTPS ( optimizations: keep-alive, gzip; SSE for live events )
        ▼
MOBCODE BACKEND  (the companion server: server.js, deployable on Render)
        │  private network connection (loopback / private VPC — never public)
        ▼
OPENCODE ENGINE (opencode serve — bound to 127.0.0.1 inside the backend host)
        │  server-side credentials only
        ▼
AI PROVIDERS
```

* The full web UI (chat, catalogue, providers, sessions, SSE) is bundled inside the APK (`www/` → `android/app/src/main/assets/public`).
* The app has **no dependency on `localhost:8090`**. On first launch it shows the
  Mobcode welcome/connect screen; the user enters their deployed backend URL
  (e.g. `https://mobcode-backend.onrender.com`). The URL is tested, then stored in
  **EncryptedSharedPreferences** and remains editable in **Settings → Server connection**.
* The Render URL is **not hardcoded** anywhere. Development HTTP (plain `http://`)
  is rejected for non-private hosts by both the web layer (`native.js`) and the
  Android network security config.
* The backend injects OpenCode authentication server-side; the Android client
  normally carries **no passwords at all** (direct-engine mode optionally uses one,
  stored only in the encrypted store).

## 5. Building

```bash
# 1. refresh the web bundle from public/
node scripts/prepare-android.mjs
npx cap sync android

# 2. builds
cd android
./gradlew assembleDebug          # → app/build/outputs/apk/debug/app-debug.apk
./gradlew assembleRelease        # signed when android/keystore.properties exists
./gradlew bundleRelease          # → app/build/outputs/bundle/release/app-release.aab

# 3. collect deliverables
bash scripts/package-android.sh   # runs the three builds + verification + dist/ copies
```

`scripts/package-android.sh` performs all three builds, verifies every artifact
(`aapt2 dump badging`, `apksigner verify`) and copies them into the required layout:

```
dist/android/debug/Mobcode-debug.apk
dist/android/release/Mobcode-release.apk
dist/android/playstore/Mobcode-release.aab
```

> Offline/cached environments: once Gradle is installed locally, skip the
> wrapper download with `GRADLE_BIN=/path/to/gradle GRADLE_ARGS="-g /path/to/gradle-home"`.
> This release was built exactly that way (JDK 21 at `/tmp/opencode/tools/jdk-21.0.2`).

## 6. Signing

* Keystore: `android/mobcode-upload.keystore` (RSA-4096, 10 000-day validity, alias `mobcode-upload`).
* Passwords live only in `android/keystore.properties` (0600, gitignored). They are **not** printed in any log.
* Both passwords were randomly generated at creation time. To rotate them, delete
  the keystore and properties file and re-run the keytool command from section 6.1
  — and understand: **rotating the upload key after first Play upload requires
  Google Play's key reset support**, so back this keystore up first.
* Gradle reads the properties at build time; without the file, a release build is
  produced **unsigned** (a warning is emitted — never distribute it for Play).

### 6.1 Recreating the keystore (write-down procedure)

```bash
cd android
keytool -genkeypair -keystore mobcode-upload.keystore -alias mobcode-upload \
  -keyalg RSA -keysize 4096 -validity 10000 \
  -dname "CN=Mobcode, OU=Mobile, O=Mobcode, L=Local, ST=Local, C=DE"
chmod 600 mobcode-upload.keystore keystore.properties
```

### 6.2 Safe backup procedure

1. Copy `mobcode-upload.keystore` **and** `keystore.properties` together — one is useless without the other.
2. Encrypt the bundle (`tar czf - <files> | age -r <recip> > mobcode-signing.age`, or an equivalent GPG/encrypted vault).
3. Store it in at least two independent places (password manager vault + offline encrypted USB).
4. Verify the backup restores the identical file (`sha256sum`) before deleting any primary copy.
5. Never commit them to git (already covered by `.gitignore`) and never paste them into chat, tickets or CI logs.

## 7. Backend deployment for the phone (Mobcode on Render)

The Android app talks to the **Mobcode companion server** (`server.js`, zero-dependency Node ≥18).
It already contains everything needed for the remote flow:

* CORS for the packaged app origins (`https://localhost`, `capacitor://localhost`…), incl. preflight.
* Same-origin proxying to a private OpenCode engine with injected basic auth.
* `/__mobcode/public` health/config endpoint used by the app's connectivity test.

Minimal Render service definition (single web service):

```
Build:        (none — plain node)
Start:        `node server.js --port $PORT --open $OPENCODE_SERVER_URL --directory $OPCODE_DIR --password $OPENCODE_SERVER_PASSWORD`
Env:          OPENCODE_SERVER_URL   = http://127.0.0.1:46000   (private loopback, NOT public)
              OPENCODE_SERVER_PASSWORD = <random secret>       (never shipped in the APK)
              OPCODE_DIR            = /data/workspace          (your private workspace)
              MOBCODE_CONFIG        = /data/mobcode.server.json (writable persistent disk)
```

Run the OpenCode engine **on the same host/container** (`opencode serve --port 46000 --hostname 127.0.0.1`)
so it shares the private network. Never expose 46000 publicly. Provider credentials stay
in the engine's own storage (`~/.opencode/auth.json` etc.) — the APK contains no keys.

## 8. Feature parity checklist

All existing Mobcode features work in Android: AI chat, prompt streaming (SSE),
dynamic model catalogue, model switching (incl. variants), agents, provider
connect/disconnect flows (key/OAuth/env hints), session list + session switching,
secure connection management, PWA assets (service worker is unused inside the
WebView but present for the web deployment).

Native additions: adaptive icon + splash, dark status bar, hardware back-button,
haptics, clipboard/share on assistant messages, encrypted connection storage,
network-recovery logic, message-loss guard (failed prompts return to the composer).
